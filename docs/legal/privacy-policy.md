## 2. Architecture-driven note: we hold references, not copies

A defining feature of Customer-Ops is that it is a **surface, not an engine**. Wherever possible it stores a *reference* to data that lives in another system of record, and fetches the detail at read time rather than retaining it:

- **Contact details** (name, email, phone, organization) live in **Contact-Ops**; Customer-Ops stores only the contact's identifier and the relationship/stage. *(One transient exception: the lead-intake buffer — see §3.)*
- **Invoices / balances** live in **Accounting-Ops**; Customer-Ops stores only an external invoice reference and a cached status for display.
- **Mailbox threads / message bodies** live in **Email-Ops** (Stalwart); Customer-Ops stores only an outbound message reference and a short subject — **never message bodies**.
- **Campaign/send data** lives in **Outreach** (Listmonk/Postiz); Customer-Ops stores only enrollment references and a cached status.
- **Meeting transcripts / summaries** live in **Meeting-Ops**; Customer-Ops reads them federated and **does not retain** them.

This materially reduces the personal data actually stored in Customer-Ops and shapes the categories below.
